# 概念架构

这份文档只描述**形状与数据流**，不含实现细节、阈值与路径。目标：让你明白这套系统由哪些部分组成、
彼此怎么说话；至于每一层怎么落地，是你自己的工程。

## 1. 一张图

```
         微信（两个真实的人）
          │                │
   ┌──────▼─────┐   ┌──────▼─────┐
   │ 通道 A     │   │ 通道 B     │      收消息、发消息、发文件、发表情
   └──────┬─────┘   └──────┬─────┘
          │                │
   ┌──────▼─────┐   ┌──────▼─────┐
   │ 人格 A     │   │ 人格 B     │      说话契约：称呼、语气、边界、什么时候不接话
   └──────┬─────┘   └──────┬─────┘
          └───────┬────────┘
           ┌──────▼──────┐
           │ 大脑（编排）│              读上下文 → 选工具 → 组回答
           └──────┬──────┘
     ┌────────────┼──────────────┬─────────────┐
     │            │              │             │
┌────▼────┐ ┌─────▼─────┐ ┌──────▼─────┐ ┌─────▼─────┐
│ 工具层  │ │ 记忆层    │ │ 日记/情绪  │ │ 控制台    │
│ 抓取/浏览器/提醒/文件 │ │ 会话/事实/向量/检索 │ │ 每晚一篇/白天打分 │ │ 状态/流水/谱系 │
└─────────┘ └───────────┘ └────────────┘ └───────────┘
                                          │
                                     浏览器（人看的）
```

## 2. 各层职责

### 通道层

- 一个通道 = 一个机器人实例 + 一个真实的人；
- 负责收发、去重、限速、断线重连、登录确认；
- **不负责**理解内容——它只把消息变成结构化事件，交给大脑。

### 人格层

- 每个 agent 一份说话契约（称呼、语气、能说什么、不能说什么、什么时候闭嘴）；
- 人格是**配置**，不是代码分支；换人格不改程序；
- 两个 agent 的人格互不可见，但共享同一本账（见记忆层）。

### 大脑（编排）

- 输入：一条消息 + 该 agent × 该身份的上下文；
- 过程：决定要不要调用工具、调哪个、调几次；工具失败要如实回到回答里；
- 输出：一串气泡（一句一条），而不是一整段——这是"像人在打字"的最低成本做法；
- 约束：一次对话有轮次与时间上限；超限就承认没做完，不要无限重试。

### 工具层

- 轻量与重量两条路：普通网页直取正文；需要点按、翻页、登录、截图才拉起真浏览器；
- 浏览器是**最贵的开口**：要单任务、有内存预算、有时长上限、只去公网；
- 文件与表情是"附件"能力，边界是白名单目录与预设类别。

### 记忆层（四层）

| 层 | 存什么 | 怎么用 |
| --- | --- | --- |
| 会话 | 最近若干轮原文 | 直接进上下文 |
| 事实 | 从对话里抽出的稳定信息（喜好、约定、关系） | 按人检索，带时效衰减 |
| 向量库 | 文档切块后的向量 | 语义检索，回答"手册里怎么写的" |
| 检索 | 以上三层的统一召回 | 按相关度 + 时效排序，取前若干条 |

原则：**记忆按人生，账本共享**。A 的事实不会被 B 的对话污染，但两个人共同经历的事，两边都能查到。

### 日记与情绪

- 白天：每条对话打一个情绪分，累积成当天的曲线；
- 夜晚：以**当天真实对话**为唯一事实来源写一篇日记（不是凭空编）；
- 日记是只读的产物：写完可以修订，但同一天不会有两篇；
- 情绪分只做参考，不参与"该不该回话"以外的决策。

### 控制台

- 只读为主：状态、计数、曲线、流水、日记、谱系；
- 唯一写入是对话页（直连大脑）与少量修复动作；
- 登录复用微信信道，不引入第二套密码体系；
- 所有页面数字都来自同一个 `/api/status`，**不许前端写死**——否则文档、库、页面必然对不上。

## 3. 数据流：一条消息

1. 通道收到消息 → 归一化（谁、哪个 agent、什么内容、何时）；
2. 写下会话记录 → 触发大脑；
3. 大脑取上下文（会话 + 事实 + 相关向量）；
4. 需要外部信息 → 调工具（失败如实回报，不静默重试）；
5. 生成回答 → 按句切分 → 交给通道逐条发出；
6. 异步：抽事实、更新情绪分、必要时写事件流。

## 4. 数据流：一次主动开口

主动开口不是"定时发消息"，而是**先判断该不该说**：

- 触发条件：长时间无话、当天情绪到位、有未完成的约定；
- 闸门：最近说过就不说、正在对话中不说、对方明确表示忙就不说；
- 内容来源：当天发生的事、记忆里的约定、日记里的未完成项；
- 失败处理：没话说就不说——沉默是允许的结果。

## 5. 为什么是这个形状

- **单进程插件 + 一个控制台线程**：2 GB 内存的机器上，多一个常驻进程就多一份 OOM 风险；
- **无前端框架、无数据库**：所有页面手写，数据落在本地 JSON / SQLite / 向量目录，备份就是拷目录；
- **登录走微信**：少一套密码就少一类泄露面，代价是控制台的安全性等于微信账号的安全性；
- **工具分层**：便宜的先上，贵的加闸门——不是"能开浏览器就全用浏览器"。

## 6. 反模式（我们踩过的）

- 每次工具调用都往聊天里推一条进度 → 刷屏泛洪；
- 上游 404 吞掉候选列表 → 大脑盲重试几十次；
- 把路径、按钮坐标写死在代码里 → 换机器就废；
- 成品定义从"能用"漂移到"有人味"却没有图纸 → 版本之间互相踩；
- 前端写死统计数字 → 文档、库、页面三份真值。

这些不是理论，是代价。你实现时可以直接绕开。
